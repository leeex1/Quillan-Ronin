# NextVerse - Quantum VM Layer

## Overview

The Quantum VM layer is responsible for managing and coordinating multiple instances of the `quantum-core-binary`. Its primary purpose is to simulate a parallel processing environment and achieve a conceptual "JQLD boost" by aggregating the performance of these instances. This layer provides a unified interface for submitting tasks to the simulated quantum resources and monitoring their status.

This system is designed for simulation and conceptual demonstration within the NextVerse ecosystem, not for actual quantum computation.

## Components

*   **`11-boot.sh`**:
    *   **Role**: This is the main startup script for the Quantum VM layer. It is responsible for:
        *   Initializing a configurable number of `quantum-core-binary` instances (defaulting to 11, based on the "11 Copy Principle").
        *   Creating instance-specific directories (`instance-X/`) and configuration files (`config.json`).
        *   Copying the `quantum-core-binary` to each instance directory.
        *   Starting each `quantum-core-binary` instance with its specific configuration.
        *   Verifying a conceptual "JQLD boost" by querying a `/boost` endpoint on each instance.
        *   **Embedding and deploying `quantum-master.py`**: The Python script for the master coordinator is written to disk from a heredoc within `11-boot.sh`.
        *   Starting the `quantum-master.py` service.
    *   **Note**: The embedding of `quantum-master.py` is an unconventional deployment method.

*   **`quantum-master.py` (generated by `11-boot.sh`)**:
    *   **Role**: This Python script acts as the central task coordinator and API gateway for the Quantum VM layer. Its responsibilities include:
        *   Providing an HTTP API for task submission and health checks.
        *   Receiving tasks via its `/execute` endpoint.
        *   Distributing (simulated) task chunks to the individual `quantum-core-binary` instances.
        *   Aggregating results and "boost" contributions from the instances.
        *   Interacting with instances over HTTP (assuming they expose an `/execute` endpoint).

*   **`quantum-core-binary`**:
    *   **Role**: This is the core computational unit that simulates quantum operations and JQLD calculation. Multiple instances of this binary are managed by the Quantum VM layer.
    *   **Details**: For more information on the `quantum-core-binary` itself, please refer to the README in the `nextverse_alpha_core_design/` directory. This binary is expected to be present in the `nextverse-platform/quantum-vm/` directory when `11-boot.sh` is executed.

*   **`instance-X/` directories**:
    *   **Purpose**: Each directory (e.g., `instance-1/`, `instance-2/`) holds the necessary files for a single `quantum-core-binary` instance. This includes:
        *   A copy of the `quantum-core-binary`.
        *   A `config.json` file tailored for that specific instance (e.g., unique `instance_id`, `ipc_port`).

## Workflow

1.  **Initialization**:
    *   The `11-boot.sh` script is executed.
    *   It sets up the specified number of instance directories.
    *   For each instance, it copies `quantum-core-binary` and generates a `config.json` with unique parameters (like port number and its share of the target JQLD boost).
    *   Each `quantum-core-binary` instance is started in the background.
    *   The script waits for a short period and then attempts to verify the JQLD boost by querying a `/boost` endpoint on each instance.

2.  **Master Service Deployment**:
    *   `11-boot.sh` writes the content of `quantum-master.py` to disk.
    *   It then starts `quantum-master.py` in the background.

3.  **Task Execution**:
    *   Clients submit tasks to `quantum-master.py` via its `/execute` HTTP endpoint.
    *   `quantum-master.py` (conceptually) divides the task and distributes these chunks to the `/execute` endpoints of the individual `quantum-core-binary` instances.
    *   Each instance processes its chunk (simulation).
    *   `quantum-master.py` gathers the results and any reported "boost" from each instance and merges them into a final response.

4.  **JQLD Boost**:
    *   The JQLD boost is a simulated concept where the combined "computational power" of all instances contributes to an aggregated performance metric. This is verified by `11-boot.sh` at startup and conceptually aggregated by `quantum-master.py` during task processing.

## Configuration

### `11-boot.sh` Environment Variables:

*   `QUANTUM_COPIES`: Number of `quantum-core-binary` instances to launch. Default: `11`.
*   `JQLD_BOOST`: Target aggregate JQLD boost value. Default: `420`.
*   `TURBO_MODE`: (Currently unused) Flag for potential future performance modes. Default: `true`.

### `instance-X/config.json` Structure:

```json
{
    "instance_id": 1, // Unique ID for the instance
    "total_copies": 11, // Total number of instances
    "jqld_params": {
        "Njq": 5, // Example JQLD parameter
        "psi_parallel": 0.8, // Example JQLD parameter
        "boost_factor": 38.18 // Calculated portion of total JQLD_BOOST for this instance
    },
    "ipc_port": 7001, // Unique port for this instance's HTTP server
    "shared_memory": "/shared/quantum-mem-1" // Conceptual shared memory path
}
```

## Key Endpoints

*   **`quantum-master.py` (listening on `http://localhost:7777`)**:
    *   `POST /execute`: Accepts JSON task data, distributes it to instances, and returns aggregated results.
    *   `GET /health`: Returns the health status of the master and the number of instances it's configured for.

*   **Individual `quantum-core-binary` instances (listening on `http://localhost:7001`, `7002`, etc.)**:
    *   `POST /execute`: (Assumed by `quantum-master.py`) Accepts a chunk of task data and returns processing results, including `boost_applied`.
    *   `GET /boost`: (Assumed by `11-boot.sh` for verification) Returns JSON with a `current_boost` field, e.g., `{"current_boost": 38.18}`.

## Important Notes

*   **Embedded Python Script**: The `quantum-master.py` script is embedded within `11-boot.sh` using a heredoc. This is generally not a standard practice for deploying Python applications and makes maintenance harder. For production or more complex scenarios, `quantum-master.py` should be a separate file.
*   **Endpoint Assumptions**:
    *   The `11-boot.sh` script assumes that each `quantum-core-binary` instance will run an HTTP server on the configured `ipc_port` and expose a `/boost` endpoint that returns its JQLD boost contribution.
    *   The `quantum-master.py` script assumes that each `quantum-core-binary` instance exposes an `/execute` endpoint for receiving task chunks.
    *   The actual implementation of these HTTP servers and endpoints must be part of the `quantum-core-binary` application.

## How to Run

1.  Ensure the `quantum-core-binary` executable is present in the `nextverse-platform/quantum-vm/` directory. This binary should be built from the `nextverse_alpha_core_design` project.
2.  Navigate to the Quantum VM directory:
    ```bash
    cd nextverse-platform/quantum-vm
    ```
3.  Make the boot script executable (if not already):
    ```bash
    chmod +x 11-boot.sh
    ```
4.  Run the boot script:
    ```bash
    ./11-boot.sh
    ```
This will start all the `quantum-core-binary` instances and the `quantum-master.py` coordinator. You can then interact with the master service at `http://localhost:7777`. Log files and PID files for each instance and the master will be created in the `nextverse-platform/quantum-vm/` directory.
